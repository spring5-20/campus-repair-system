# 校园报修协作系统
## 学生六人前后端协作项目 PRD

> 供产品经理指挥 3 人前端组与 3 人后端组执行、联调和验收

**文档版本：**V1.0（可执行基线）

**发布状态：**已冻结范围，可进入分支开发；接口变更须走变更流程

**产品负责人：**课程产品经理（教师）

**研发团队：**前端组 3 人｜后端组 3 人

**发布日期：**2026-08-23

**对应仓库：**mini-repair-system

**交互基线：**campus-repair-student-complete-prototype.html

**项目一句话** 学生提交校园故障，维修人员接单或被指派后处理，学生验收关闭，管理员通过数据看板和审计日志管理全过程。

## 产品经理的四条红线

- OpenAPI 是接口唯一事实源：任何路径、字段、状态码变化，先改 docs/openapi.yaml，再改代码。
- 权限必须由后端校验：前端隐藏按钮只改善体验，不能代替 401/403 权限控制。
- 状态不得跳转：所有工单严格遵循本 PRD 的状态机，并写入操作日志。
- 没有测试证据不算完成：每个 PR 必须附构建、接口测试或截图；合并前执行 npm run verify。

# 1. 产品概述

## 1.1 背景与问题

普通 CRUD 项目容易只展示页面和接口，缺少真实业务约束。校园报修具备清晰的角色分工、权限边界、状态流转、异步数据库访问和可验证的前后端联调过程，适合作为求职作品中的小型业务闭环。

## 1.2 产品目标

- 业务闭环：完成“学生提交—维修接单/指派—完成维修—学生验收”的主流程。
- 协作闭环：六人通过独立分支、OpenAPI 契约、Pull Request 和联调清单完成一次真实协作。
- 技术闭环：前端处理状态与异常，后端使用 FastAPI、SQLAlchemy Async 与 aiomysql 实现持久化和权限控制。
- 求职表达：每位学生都能说明需求、接口、实现、测试和自己对 Codex 输出的人工检查。

## 1.3 成功标准

#### 表 1-1　产品成功标准

## 1.4 非目标

- 不做多学校、多租户、组织架构和复杂用户管理。
- 不做支付、采购、库存、工时结算、地图导航或真实短信/微信通知。
- 不在本轮接入对象存储、Redis、WebSocket、AI 自动派单或生产级运维体系。
- 附件在本轮只做前端选择、校验和本地预览；真实上传与后端存储属于 P2 扩展。

# 4. 业务流程与状态机

## 4.1 主流程

1. 学生填写标题、描述、分类、位置和优先级，提交后生成 PENDING 工单。
2. 维修人员主动接单，或管理员把 PENDING 工单指派给维修人员；工单进入 PROCESSING。
3. 负责人完成维修并提交结果，工单进入 RESOLVED，等待报修学生确认。
4. 学生确认恢复后关闭工单，工单进入 CLOSED；管理员可在异常场景代为关闭。
5. 学生可在尚未接单时取消本人工单，进入 CANCELLED；管理员也可取消异常待处理工单。

## 4.2 状态定义

#### 表 4-1　状态字典

| **状态** | **中文显示** | **含义** | **允许的下一状态** |
| --- | --- | --- | --- |
| PENDING | 待接单 | 已提交，尚未确定负责人 | PROCESSING / CANCELLED |
| PROCESSING | 处理中 | 已由维修人员接取或管理员指派 | RESOLVED |
| RESOLVED | 待确认 | 维修完成，等待学生验收 | CLOSED |
| CLOSED | 已关闭 | 学生已确认，业务闭环 | 无（终态） |
| CANCELLED | 已取消 | 未接单前被学生或管理员取消 | 无（终态） |

## 4.3 状态迁移与授权

#### 表 4-2　状态迁移表

| **起始** | **动作** | **目标** | **允许角色** | **附加条件** | **日志动作** |
| --- | --- | --- | --- | --- | --- |
| — | 创建 | PENDING | 学生 | 创建人=当前用户 | CREATE |
| PENDING | 接单 | PROCESSING | 维修人员 | 工单未被他人接取 | ACCEPT |
| PENDING | 指派 | PROCESSING | 管理员 | 目标用户角色=维修人员 | ASSIGN |
| PROCESSING | 完成维修 | RESOLVED | 负责人/管理员 | 维修人员只能处理本人任务 | RESOLVE |
| RESOLVED | 验收关闭 | CLOSED | 报修人/管理员 | 学生只能关闭本人工单 | CLOSE |
| PENDING | 取消 | CANCELLED | 报修人/管理员 | 学生只能取消本人工单 | CANCEL |

**并发处理** 接单、指派和状态更新必须在数据库事务内重新查询当前状态；若状态已被其他请求改变，返回 409，前端刷新详情并提示用户。

## 5.2 全局交互规范

- 加载：按钮提交时禁用并显示处理中；列表请求显示骨架或加载状态，避免重复提交。
- 空状态：明确说明“当前没有符合条件的工单”，并提供清空筛选或提交报修入口。
- 错误：展示可理解的 message；网络失败提供重试；不得以白屏或控制台报错代替反馈。
- 401：清除 token 和用户信息，保留当前路径作为可选回跳参数，返回登录页。
- 403：提示没有权限，不自动改写本地状态；必要时重新拉取详情。
- 筛选：keyword、status、category、page、pageSize 同步到 URL，刷新后保持。
- 提交成功：创建、接单、指派、状态变更和留言成功后，以后端返回数据覆盖本地数据。

# 7. 接口契约

## 7.1 统一规范

- 服务地址：http://localhost:3000/api；前端开发环境通过 Vite 代理访问 /api。
- 鉴权：Authorization: Bearer <JWT>；JWT 内只放必要身份信息，后端以数据库用户为准。
- 成功和业务错误统一返回 {code, message, data}；HTTP 状态码反映真实结果。
- 日期时间使用 ISO 8601；字段命名使用 camelCase；数据库字段可使用 snake_case，由 Schema 映射。
- 参数错误 422、未登录 401、越权 403、不存在 404、状态并发冲突 409。
```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

## 7.3 分页接口（冻结草案）

```http
GET /api/tickets?page=1&pageSize=10&status=PENDING&category=网络故障&keyword=宿舍
```

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [Ticket],
    "total": 23,
    "page": 1,
    "pageSize": 10,
    "pages": 3
  }
}
```

约束：page≥1；pageSize 允许 10/20/50，默认 10；keyword 搜索工单编号、标题和位置；排序默认 updatedAt DESC。学生的 total 和 items 均只统计本人数据。

| PATCH /tickets/{id}/assignee | body: {assigneeId}; 返回 Ticket | 仅管理员；目标为维修角色；PENDING→PROCESSING；写 ASSIGN 日志 |
| GET /tickets/{id}/logs | data: TicketLog[] | 按 createdAt ASC；仅返回不可修改的审计记录 |

**契约任务** BE1/BE2/BE3 在编码前先更新 docs/openapi.yaml；FE2/FE3 依据契约生成或手写 TypeScript 类型。接口评审通过后再合并实现。

# 8. 数据模型与后端要求

## 8.1 核心实体

#### 表 8-1　数据字典摘要

| **实体** | **关键字段** | **约束/关系** |
| --- | --- | --- |
| User | id, username, displayName, passwordHash, role | username 唯一；密码只存哈希 |
| Ticket | id, ticketNo, title, description, category, location, priority, status, reporterId, assigneeId, assignedBy, assignedAt, createdAt, updatedAt | reporter 必填；assignee 可空；ticketNo 唯一 |
| TicketComment | id, ticketId, authorId, content, createdAt | content 去空格后 1–500；关联可见工单 |
| TicketLog | id, ticketId, actorId, action, fromStatus, toStatus, detail, createdAt | 只增不改；关键状态动作必须记录 |

## 8.2 FastAPI 与异步数据库约束

- 所有数据库 I/O 使用 AsyncSession；路由、Service、Repository 均不得调用同步 ORM I/O。
- Session 通过 FastAPI Depends 提供；一次请求一次 Session，不在并发任务之间共享。
- 查询关系使用 selectinload 等显式加载，避免异步隐式 lazy loading。
- 接单、指派、状态迁移和日志写入放在同一事务；异常回滚，成功后提交。
- 请求与响应使用独立 Pydantic v2 Schema；禁止直接把 ORM 对象结构当作接口契约。
- 课堂环境可用 metadata.create_all；正式升级路线使用 Alembic。
- 自动测试使用 aiosqlite，不依赖本机 MySQL；MySQL 联调作为独立验收步骤。

## 8.3 索引与数据一致性

- Ticket：ticketNo 唯一索引；status、reporterId、assigneeId、updatedAt 建查询索引。
- 分页查询先应用角色数据范围，再应用筛选、排序、limit/offset；total 与 items 使用同一过滤条件。
- 指派与接单必须防止重复认领；必要时使用行锁或条件更新，并用 409 表达冲突。
- 关闭和取消后的终态不可再次变更；日志与工单状态必须同事务一致。

# 12. 验收标准与测试场景

## 12.1 Definition of Done

- 需求编号、实现范围和验收口径一致；无未说明的范围外功能。
- OpenAPI 与实际接口一致；前端 TypeScript 类型与响应对象一致。
- 主路径、权限失败、参数失败和状态冲突均有测试或可重复的联调步骤。
- 后端测试通过；前端 TypeScript 检查和 Vite 构建通过；npm run verify 通过。
- PR 已由至少一名非作者评审；所有高优先级评论关闭。
- README、测试账号、启动命令和演示步骤保持可用；没有真实密钥或个人数据。

# 13. 产品经理的日常指挥机制

## 13.1 每日节奏

- 每日 10 分钟站会：昨天完成、今天目标、阻塞、接口变化；只讲事实和证据。
- 每日下班前更新任务看板：需求 ID、Owner、分支/PR、状态、风险、下一步。
- D2、D5、D8 固定评审：接口冻结、小组集成、三角色验收；其余会议按问题触发。
- PM 只接受带复现步骤的缺陷；组员只接受带需求 ID 和验收口径的新增要求。

## 13.2 需求变更流程

1. 提出变更：写清问题、用户价值、受影响需求/页面/接口、期望完成时间。
2. 影响评估：前端组长、后端组长分别给出工期、风险、测试与兼容性影响。
3. 产品决策：PM 选择纳入当前迭代、降为 P2，或拒绝；不得口头插单。
4. 同步事实源：更新 PRD、原型和 OpenAPI，标记版本与变更记录。
5. 实施与回归：按新验收口径开发，并重新测试所有受影响场景。
**接口冻结后** 字段改名、响应结构变化、状态新增或权限变化都视为重大变更，必须由 PM、前端组长、后端组长三方确认。
